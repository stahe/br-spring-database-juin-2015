    3.2. Etapas de operação de um banco de dados

    Na arquitetura acima, a exploração de um banco de dados pelo programa de console envolve as seguintes etapas:

    1. carregamento do driver JDBC do banco de dados;
    1. abertura de uma conexão com o banco de dados;
    2. execução de um comando SQL no banco de dados e processamento dos resultados do comando SQL;
    3. fechamento da conexão;

    A etapa 1 é executada apenas uma vez. As etapas 2 a 4 são repetidas. Observe que não se deixa uma conexão aberta. Ela é fechada assim que não for mais necessária.

    3.2.1. etapa 1 — carregamento na memória do driver JDBC

    O código

    
        // carregando o driver JDBC
        try {
            Class.forName(nom de la classe du pilote JDBC);
        } catch (ClassNotFoundException e1) {
             // tratar a exceção
}

    A operação da linha 3 tem como objetivo carregar na memória o driver JDBC do banco de dados. Essa operação precisa ser realizada apenas uma vez. Repeti-la, no entanto, não causa erros. A classe do driver JDBC é procurada no Classpath do projeto. Portanto, no projeto do Eclipse, o [jar], que contém a classe do driver JDBC, deve ter sido incluído no Classpath do projeto.

    3.2.3. Etapa 3 — emissão das ordens SQL e [SELECT]

    Uma vez estabelecida a conexão, é possível emitir ordens SQL. A forma de gerenciar ordens de leitura [SELECT] difere daquela utilizada para as operações de atualização [UPDATE, INSERT, DELETE]. Começamos pelas ordens SQL e [SELECT]:

    O código

    
Connection connexion = null;
        PreparedStatement ps = null;
        ResultSet rs = null;

            connexion = DriverManager.getConnection(url, user, passwd);

            connexion.setAutoCommit(false);

            connexion.setReadOnly(true);

    • linhas 8, 10: abertura de uma transação (linha 8) no modo somente leitura (linha 10). Uma transação é uma sequência de ordens SQL que ou são todas bem-sucedidas ou todas falham. Assim, em uma transação com N ordens SQL, se a ordem I+1 falhar, as I anteriores serão canceladas. Para uma operação de leitura, não é necessária uma transação. No entanto, criar uma transação somente leitura pode permitir que certas ordens SGBD realizem algumas otimizações;
    • linha 12: uso de um [PreparedStatement]. Um [PreparedStatement] normalmente possui parâmetros indicados pelo caractere ?. Aqui, ele não os possui. Um [PreparedStatement] é uma ordem preparada pelo SGBD. Essa preparação tem um custo e é feita apenas uma vez. Em seguida, essa ordem preparada é executada pelo SGBD com diferentes parâmetros efetivos que substituirão os parâmetros formais ?. Vale ressaltar que é preferível nomear as colunas desejadas em vez de usar a notação * para obter todas as colunas. Ao especificar o nome das colunas, é possível obter seus valores a partir de sua posição na consulta SELECT;
    • linha 13: execução do [PreparedStatement]. Recupera-se um objeto do tipo [ResultSet];

    Um objeto do tipo [ResultSet] representa uma tabela, ou seja, um conjunto de linhas e colunas. Em um determinado momento, só se tem acesso a uma linha da tabela, chamada de linha atual. Durante a criação inicial do [ResultSet], não há linha atual. É necessário executar uma operação [ResultSet.next()] para obtê-la. A assinatura do método next é a seguinte:

        boolean next()

    Esse método tenta avançar para a próxima linha do [ResultSet] e retorna true se for bem-sucedido; caso contrário, retorna false. Se for bem-sucedido, a próxima linha se torna a nova linha atual. A linha anterior é perdida e não será possível voltar atrás para recuperá-la.

    A tabela [ResultSet] possui colunas denominadas labelCol1, labelCol2, ... especificadas na consulta [SELECT] executada. Com a consulta:

    SELECT ID as myId, NOM as myNom, CATEGORIE as myCategorie, PRIX as myPrix, DESCRIPTION as myDescription FROM PRODUITS
    • a coluna [ID] será transferida para uma coluna do [ResultSet] chamada [myId];
    • a coluna [NOM] será transferida para uma coluna do [ResultSet] chamada [myNom];
    • ...

    No exemplo acima, os identificadores [myCol] são chamados de rótulos de coluna. Na ausência desses rótulos, os nomes das colunas do [ResultSet] dependem do SGBD. Quando o [SELECT] opera em uma única tabela, os rótulos das colunas serão, por padrão, os nomes das colunas solicitadas pelo SELECT. O problema surge quando o [SELECT] opera em várias tabelas e nessas tabelas existem nomes de colunas idênticos, como no exemplo a seguir:

    SELECT PRODUITS.NOM, CATEGORIES.NOM FROM PRODUITS, CATEGORIES WHERE PRODUITS.CATEGORIE_ID=CATEGORIES.ID

    supondo que a tabela [PRODUITS] tenha uma chave estrangeira para a tabela [CATEGORIES], representada pela relação [Produits].CATEGORIE_ID --> [CATEGORIES].ID, e que as tabelas [PRODUITS] e [CATEGORIES] tenham ambas um campo [NOM]. Nesse caso, os nomes atribuídos na tabela [ResultSet] às colunas [PRODUITS.NOM] e [CATEGORIES.NOM] dependem da tabela SGBD. Para a portabilidade entre o SGBD, é necessário, portanto, utilizar rótulos de colunas aqui, e escreveremos:

    
SELECT PRODUITS.NOM as p_NOM, CATEGORIES.NOM as c_NOM FROM PRODUITS, CATEGORIES WHERE PRODUITS.CATEGORIE_ID=CATEGORIES.ID

    Para explorar os diferentes campos da linha atual do [ResultSet], dispomos dos seguintes métodos:

    Type getType("labelColi")

    para obter a coluna denominada “labelColi” da linha atual e, portanto, a coluna do [SELECT] que possui esse rótulo. Type designa o tipo do campo coli. É possível utilizar os seguintes métodos [getType]: getInt, getLong, getString, getDouble, getFloat, getDate, ... Em vez de usar o nome da coluna, pode-se usar sua posição na consulta [SELECT] executada:

    Type getType(i)

    onde i é o índice da coluna desejada (i>=1).

    3.2.4. Etapa 3 — emissão das ordens SQL e [INSERT, UPDATE, DELETE]

    As ordens SQL e [INSERT, UPDATE, DELETE] são operações de atualização: elas modificam o banco de dados, mas não retornam nenhuma linha. A única informação fornecida é o número de linhas afetadas pela operação de atualização.

    O código

    
Connection connexion = null;
        PreparedStatement ps = null;
        try {
            // abrir conexão
            connexion = DriverManager.getConnection(url, user, passwd);
            // início da transação
            connexion.setAutoCommit(false);
            // no modo leitura/gravação
            connexion.setReadOnly(false);
            // atualização da tabela
            ps = connexion.prepareStatement("UPDATE PRODUITS SET PRIX=PRIX*1.1 WHERE CATEGORIE=?");
            // categoria 1
            ps.setInt(1, 10);
            // execução
            int nbLignes=ps.executeUpdate();
            // confirmação da transação
            connexion.commit();
        } catch (SQLException e1) {
            // tratando a exceção
            doCatchException(connexion, e1);
        } finally {
            // processando o finally
            doFinally(null, ps, connexion);
        }
    }
    • linha 9: a conexão é utilizada para leitura e gravação;
    • linha 11: um [PreparedStatement] com 1 parâmetro (simbolizado por ?). É possível ter vários parâmetros. Eles são numerados a partir de 1;
    • linha 13: atribui-se seu valor ao único parâmetro. O primeiro parâmetro de [setType] é a posição do parâmetro no [PreparedStatement] (1, 2, ...) e o segundo é o valor que lhe é atribuído. É possível utilizar os métodos [setInt, setLong, setFloat, setDouble, setString, setDate, ...];
    • linha 15: utiliza-se o método [executeUpdate] e não o [executeQuery], reservado para as ordens SELECT. O método retorna o número de linhas afetadas pela operação. Pode ser 0.
    • linha 17: a transação é validada;

    3.2.5. etapa 4 — encerramento da conexão

    Uma conexão deve ser fechada o mais rápido possível em um contexto multiusuário, pois um SGBD aceita um número limitado de conexões abertas. Nos exemplos anteriores, ela era fechada na cláusula [finally] das operações SQL, de modo que fosse fechada independentemente de ter ocorrido uma exceção ou não.

    3.3.5. A exceção [UncheckedException]

      

    Consideremos a seguinte arquitetura:

    • a camada [JDBC] lança exceções do tipo [SQLException]. Essa exceção deve subir pelas camadas até atingir a camada mais alta, neste caso, a camada de testes;

    A camada [DAO] poderia simplesmente permitir que a [SQLException] fosse encaminhada até a camada de testes. Mas, como essa exceção é não controlada (decorre diretamente de [Exception]), isso implicaria que a interface [IDao] da camada [DAO] fosse a seguinte:

    
public interface IDao {

    // adicionar produtos
    public List<Produit> addProduits(List<Produit> produits) throws SQLException;

    // lista de todos os produtos
    public List<Produit> getAllProduits() throws SQLException;

    // um produto específico
    public Produit getProduitById(int id) throws SQLException;

    public Produit getProduitByName(String name) throws SQLException;

    // atualização de vários produtos
    public int updateProduits(List<Produit> produits) throws SQLException;

    // exclusão de todos os produtos
    public int deleteAllProduits() throws SQLException;

    // exclusão de vários produtos
    public int deleteProduits(int[] ids) throws SQLException;
}

    E isso é muito incômodo, pois nos impede de implementar a interface [IDao] por meio de uma classe que lançaria uma exceção diferente.     O método [delete] utiliza transações. Uma transação permite agrupar ordens SQL que devem ser todas executadas com sucesso ou todas canceladas. Há quatro operações a serem consideradas:

    • início de uma transação: [connexion.setAutoCommit(false)];
    • fim de uma transação com sucesso: [connexion.commit()]. Nesse caso, todas as operações realizadas na BD durante a transação são validadas;
    • fim de uma transação com falha: [connexion.rollback()]. Nesse caso, todas as operações realizadas no BD durante a transação são canceladas;

    Vamos utilizar uma fonte de dados implementada pela classe [org.apache.tomcat.jdbc.pool.DataSource]. Essa classe utiliza um pool de conexões, ou seja, um conjunto de conexões abertas:

    • quando o pool é instanciado, um determinado número de conexões é aberto com o banco de dados. Esse número é configurável;
    • quando o código Java abre uma conexão, ela é fornecida pelo pool;
    • quando o código Java fecha uma conexão, ela é devolvida ao pool;

    No final das contas, as conexões são abertas apenas uma vez, o que melhora o desempenho do acesso ao banco de dados. A fonte de dados será definida em uma classe de configuração do Spring

        // possível exceção
        DaoException daoException = null;
        // lista de produtos
        List<Produit> produits = new ArrayList<Produit>();
        try (Connection connexion = dataSource.getConnection()) {
            // início da transação
            connexion.setAutoCommit(false);
            // no modo somente leitura
            connexion.setReadOnly(true);
            // a tabela [PRODUITS] está sendo lida
            try (PreparedStatement ps = connexion.prepareStatement(ConfigJdbc.V2_SELECT_ALLPRODUITS)) {
                try (ResultSet rs = ps.executeQuery()) {
                    while (rs.next()) {
                        produits.add(new Produit(rs.getInt(1), rs.getString(2), rs.getInt(3), rs.getDouble(4), rs.getString(5)));
                    }
                }
                // fim da transação
                connexion.commit();
                // retorno ao modo padrão
                connexion.setAutoCommit(true);
            } catch (SQLException e1) {
                // a transação é cancelada
                daoException = doRollback(connexion, e1, 111);
            }
        } catch (SQLException e2) {
            // tratando a exceção
            if (daoException == null) {
                daoException = new DaoException(112, e2, simpleClassName);
            }
        }
        // exceção?
        if (daoException != null) {
            throw daoException;
        }
        // resultado
        return produits;

    portée <T> type_résultat m(... , T value1, ...){
...
    T value2=...
}

    No código do método m, encontraremos dados do tipo T. O método m de uma instância c de uma classe C pode, então, ser chamado da seguinte maneira:

    type_résultat r=c.<T1>m(..., T1 value1, ..) ;

    onde T1 é o tipo efetivo que substituirá o tipo formal T do método m. Na maioria das vezes, o compilador é capaz de deduzir o tipo T1 a partir dos argumentos do método m. Portanto, a instrução anterior será, na maioria das vezes, simplificada para:

    type_résultat r=c.m(..., T1 value1, ..) ;

    Voltemos ao método [affiche]. Ele exibe uma lista de elementos do tipo T. Isso é possível porque o mapeador jSON utilizado na linha 4 é capaz de gerar a representação jSON de qualquer tipo de objeto. Neste exemplo específico, o único tipo T utilizado será o tipo [Produit].

    // exibição da lista de produtos
    private void affiche(Object o) throws JsonProcessingException {
            System.out.println(jsonMapper.writeValueAsString(o));
